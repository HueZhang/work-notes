

# 📝 SQL Server 存储过程调试与异常捕获指南

在维护复杂的存储过程时，经常会遇到“偶尔报错”、“特定参数报错”或“没有详细报错行号”的抓狂情况。由于存储过程通常包含大量动态 SQL 和游标，传统的断点调试往往很难直接奏效。以下是总结的几套实用排错方法论：

### 一、 建立全局防线：TRY...CATCH 块
对于任何核心业务逻辑的存储过程，建议都在主干逻辑外围包裹 `TRY...CATCH` 结构。它不仅能防止程序崩溃时抛出难懂的底层错误，更能精准定位出错行。

**标准写法：**
```sql
CREATE PROCEDURE sp_MyProcedure
AS
BEGIN
    BEGIN TRY
        -- 你的业务逻辑代码主体
        
    END TRY
    BEGIN CATCH
        -- 捕获异常信息
        SELECT 
            ERROR_NUMBER() AS 错误编号,
            ERROR_SEVERITY() AS 严重级别,
            ERROR_STATE() AS 错误状态,
            ERROR_PROCEDURE() AS 报错存储过程,
            ERROR_LINE() AS 报错行号,  -- 核心！直接告诉你是第几行崩的
            ERROR_MESSAGE() AS 错误详情;
            
        -- 可选：将错误日志插入日志表，便于事后追溯
        -- INSERT INTO ErrorLog (...) VALUES (...)
    END CATCH
END
GO
```
**⚠️ 避坑提醒：**
1. `TRY...CATCH` 不能跨越 `GO` 批处理关键字。
2. 某些严重级别极高（如硬件故障）或编译期错误（如语法错误），`CATCH` 是捕获不到的。

---

### 二、 动态 SQL 排雷：Print 或 Select 变量
动态 SQL（使用 `EXEC(@sql)` 执行）是存储过程报错的“重灾区”。因为它是将字符串拼接后执行，报错行号通常只会指向 `EXEC` 那一行，完全不知道内部哪一句出了问题。

**排查方法：**
在执行 `EXEC(@sql)` 之前，将拼接好的 `@sql` 打印出来。
```sql
    SET @sql = 'UPDATE Table1 SET ... WHERE id=' + CAST(@id AS VARCHAR);
    
    -- 👇 调试神器：把最终执行的语句打印出来看
    PRINT '----- 即将执行的SQL -----';
    PRINT @sql; 
    
    EXEC sp_executesql @sql; -- 建议用 sp_executesql 代替 EXEC
```
**排查点：**
*   **截断问题**：检查 `@sql` 的长度。SQL Server 在拼接 `varchar` 时，如果超过 8000 字符，会**隐式截断**！导致最后的语句残缺不全。解决办法是强制转换为 `CAST(... AS NVARCHAR(MAX))`。
*   **单引号问题**：拼接时有没有漏掉单引号，导致生成的语法错误。

---

### 三、 排查“幽灵报错”：常见异常场景分析
很多时候存储过程报错，是因为特定参数触发了隐藏的数据问题：

1.  **“将截断字符串或二进制数据” (Error 8152)**
    *   **原因**：数据长度超限。
    *   **排查**：检查临时表（`#Table`、`@Table`）中定义的 `varchar` 长度是否过小；如果字段已经是 `max` 还报错，请高度怀疑是动态 SQL 拼接超过 8000 字节被截断。
2.  **“将 varchar 转换为 int 等类型的转换失败”**
    *   **原因**：隐式类型转换失败。比如某字段存了 `'A123'`，你却尝试用 `SUM()` 去求和，或者尝试将其隐式插入到整型列。
    *   **排查**：重点检查 `INSERT INTO ... SELECT ...` 语句，或者 `ISNULL(IntColumn, '')` 这种把空字符串给数字类型的反人类写法。

---

### 四、 终极追踪：使用 SQL Server Profiler
如果以上方法都找不到问题，或者存储过程是嵌套调用的，可以使用 SQL Server 自带的跟踪工具（Profiler 或 XEvent）。
*   开启跟踪，监听 `SQL:BatchCompleted` 和 `SP:StmtCompleted` 事件。
*   过滤特定的数据库或应用名。
*   输入触发报错的参数执行一次，在 Profiler 中可以直接看到**最底层报错的那一句完整的 SQL 语句**。

### 💡 总结心法
1. **遇事不决先打印**：多写 `PRINT`，少猜。
2. **缩小范围法**：通过二分法排查参数（比如测试单选正常、多选报错，那就查多选带来的数据量/数据长度问题）。
3. **动态 SQL 永远要小心**：能用参数化查询（`sp_executesql` 传参）就不要硬拼字符串。
